# CheckoutLatencySLOBreach

**severity: page ／ team: checkout**

結帳在 300 毫秒內完成的比例連續 10 分鐘低於 95%（Day 2 訂的延遲 SLO）。

## 先確認

1. 打開「結帳服務 SLI」儀表板，看右邊那張延遲圖
2. **P50 有沒有跟著動？**
   - P50 也上去了 → 全部的人都慢，通常是下游整體變慢或資源不足，往下看第 3 點
   - P50 平的、只有 P95/P99 上去 → 長尾，少數請求特別慢，跳到第 4 點

## 全部都慢

- 看節點的 USE 三張圖（CPU 使用率、飽和度、記憶體）
- `kubectl get pods` 看有沒有 Pod 在重啟
- `kubectl top pods` 看有沒有人吃滿資源

## 長尾

1. 在延遲圖上點 P99 附近的 exemplar 小點 → View trace
2. 看火焰圖，時間花在哪一段
3. 常見形狀：
   - **階梯狀，一排同樣的下游呼叫** → N+1，查 `cart.item_count` 這類屬性找觸發條件
   - **大段空白** → 那段沒有埋點，或是整台機器停頓
4. TraceQL 驗證假設，例如 `{ span.cart.item_count > 5 && duration > 300ms }`

## 緩解

- 確認是最近一次部署造成的話，先回滾
- N+1 這類程式問題沒辦法即時修，先確認影響範圍（多少比例的請求），再決定要不要回滾
